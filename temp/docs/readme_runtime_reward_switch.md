# Runtime Reward-Mode Switch (UPARAM(9)) — Migration Notes

**Author:** wangyuning
**Branch:** `dev_yw_cost`
**Date:** 2026-07-19
**Case implemented first:** `envs/cases/mini_channel` (local test case)

---

## Motivation

Previously the reward function was chosen at **compile time** with the `NETGAIN`
preprocessor flag in `PPLIST`:

```bash
# drag reduction (dUdy)          -> PPLIST without NETGAIN
# net energy saving (tau/pw/v3)  -> PPLIST with    NETGAIN
```

This was inflexible: switching between drag-reduction and net-energy-saving reward
required editing the compile script and **recompiling the whole case**. Worse, the
compile flag and the Python `Runner.reward_fn` config had to be kept in sync *by
hand* — if Fortran was built with `NETGAIN` (sends 3 MPI buffers) but Python
expected `dudy` (receives 1), or vice versa, the MPI exchange **deadlocked**
(documented in `readme_POL_netgain.md`).

The reward mode is now a **runtime user parameter** (`UPARAM(9)`), written into the
`.par` file directly from `Runner.reward_fn`. One source of truth → Fortran and
Python can never disagree, and no recompile is needed to switch.

---

## Design

| Layer | Selector | Values |
|---|---|---|
| Python config | `Runner.reward_fn` (`src/configs.py`) | `'dudy'` \| `'net_gain'` |
| `.par` file   | `userParam09` | `0` \| `1` |
| Fortran       | `UPARAM(9)` | `0 = dudy`, `1 = net_gain` |

**Single source of truth:** `userParam09` is derived from `reward_fn` when the
`.par` is generated (`src/lib/nek_utils.py :: rewrite_REA_v19`). Nothing else sets
it, so the Fortran reward path and the Python `MPI.Recv` path are always consistent.

**Safe default:** Nek zeroes `uparam(1:20)` at startup (`core/reader_par.f`), so an
old `.par` without `userParam09` reads `0` → `dudy` mode. Backward compatible.

**No memory cost:** the net-gain arrays `rwd_tau/rwd_pw/rwd_v3` are declared
*unconditionally* in `inc_src/DRL` (common block `/drl_netgain/`), and both
`compute_dudy` and `compute_netGain` were already always compiled. The old
`#ifdef NETGAIN` only toggled the one-line dispatch and the send branch, so moving
to a runtime `if` is essentially free.

## UPARAM slot map (unchanged 1–8, new 9)

| Slot | Meaning | Python source |
|---|---|---|
| UPARAM(1) | ndrl (DRL substeps) | `Simulation.ndrl` |
| UPARAM(2) | znmf_avg | `Simulation.znmf_avg` |
| UPARAM(3) | y_sensing | `Simulation.y_sensing` |
| UPARAM(4) | retau | `Simulation.retau` |
| UPARAM(5) | ys_bdf | `Simulation.ys_bdf` |
| UPARAM(6) | amp_bdf | `Simulation.amp_bdf` |
| UPARAM(7) | ret_bdf | `Simulation.ret_bdf` |
| UPARAM(8) | gll_unique | `Simulation.gll_unique` |
| **UPARAM(9)** | **reward mode (0=dudy, 1=net_gain)** | **`Runner.reward_fn`** |

`reader_par.f` reads `userParam01..20`, so slot 9 is valid; slots up to 20 remain free.

## Files changed (all marked with `#[MOD]` / `!#[MOD]`)

### Fortran — `envs/cases/mini_channel/`

**`drl/drl_reward.f` — `drl_reward()`**
Replaced the compile-time dispatch with a runtime switch:
```fortran
!#[MOD] was: #ifdef NETGAIN / compute_netGain / #else / compute_dudy / #endif
        reward_mode = nint(UPARAM(9))
        ...
        if (reward_mode.eq.1) then
                call compute_netGain(i_evolv)
        else
                call compute_dudy(i_evolv)
        endif
```
`nint()` is used (not `.eq.1.0`) to avoid float-equality issues; new local
`integer reward_mode` declared. The mode is echoed in the `[REWARD] INQURY` print.

**`drl/drl_IO.f` — `drl_reward_out()`**
Replaced the `#ifdef NETGAIN` send branch with the same runtime `if`. Reads its own
`reward_mode = nint(UPARAM(9))` with the **identical** convention as
`drl_reward()` — the two MUST agree (mode 1 populates *and* sends 3 buffers;
mode 0 populates *and* sends 1). New local `integer reward_mode` declared.

**`drl/drl_init.f`**
Added a startup echo for auditability (runtime choice is otherwise invisible):
```fortran
!#[MOD] Echo runtime reward mode (UPARAM(9): 0=dudy, 1=net_gain)
        if (NID.eq.0) print *, "YW: REWARD MODE=",nint(UPARAM(9))
```

**`compile_script`**
Removed `NETGAIN` from `PPLIST` (now `"MPIIO DRL TSRS GAINMONITOR"`) and documented
why. `GAINMONITOR` is left as a compile flag; the monitor lives inside
`compute_netGain`, so it only fires in `net_gain` mode — which is the intended
behaviour. **A recompile is required once** to pick up the source changes; after
that, switching reward modes needs no recompile.

> Note: `.state` and `makefile` still list `NETGAIN` but are build artifacts
> regenerated by `makenek`; they refresh on the next compile.

### Python

**`src/lib/nek_utils.py` — `rewrite_REA_v19()`**
- Added the missing `userp += 1` after `gll_unique` (slot 8) before writing slot 9.
- Writes `userParam09` from `Runner.reward_fn` via `self.drl`:
```python
reward_fn = getattr(self.drl, 'reward_fn', 'dudy')
if reward_fn not in ('dudy', 'net_gain'):
    raise ValueError(...)          # fail fast on typo, not at MPI deadlock
reward_mode = 1 if reward_fn == 'net_gain' else 0
fpar.write('userParam%02d = %s \n' % (userp, reward_mode))
```

**`src/configs.py`** — updated the `reward_fn` comment (no longer needs a compile flag).

## How to use

In the YAML / config, set the runner reward function:

```yaml
runner:
  reward_fn: net_gain   # or: dudy
  reward_alpha: 1.0     # (net_gain only) weight on 1 - tau_w/tau_ref
  reward_beta:  1.0     # (net_gain only) weight on -|p'v|/tau_ref
  reward_gamma: 1.0     # (net_gain only) weight on -0.5|v^3|/tau_ref
```

That value is written to `<case>.par` as `userParam09` at setup. No recompile.
Confirm in the run log:

```
YW: REWARD MODE=  1        # from drl_init
[REWARD] INQURY  MODE=  1  # from drl_reward each policy step
```

and in the generated `<case>.par`:

```
userParam09 = 1
```

## Evaluation always runs `net_gain` (run-script) — and why both sides must agree

`execs/run-script`'s `evaluate` branch **intentionally forces `reward_fn=net_gain`**,
regardless of the reward the policy was trained on. This is a deliberate choice:
`net_gain` reports all three reward components (`R_tau`, `R_pw`, `R_v3`), so an
evaluation logs strictly more information — even a `dudy`-trained policy is scored
with the full net-energy-saving breakdown.

**Critical requirement:** `reward_fn` is the single source of truth for the MPI
buffer count — it sets `userParam09`, which decides whether Fortran sends **1**
buffer (`dudy`) or **3** (`net_gain`). The `evaluate` branch runs *two* Python
launches, and **both** must be forced to `net_gain` together:

| Launch | Role | Override needed |
|---|---|---|
| `python -m nek_MARL initial …` | Writes the `.par` (→ `userParam09` → Fortran buffer count) | `runner.reward_fn=net_gain` |
| `python -m nek_MARL evaluate …` | Python receive path (1 vs 3 `MPI.Recv`) | `runner.reward_fn=net_gain` |

If only **one** side is forced, the two disagree and MPI deadlocks:

> **Bug seen 2026-07-19 (fixed):** the `initial` step inherited `reward_fn: dudy`
> from the yaml (wrote `userParam09 = 0` → Fortran sends 1 buffer), while only the
> `evaluate` step was hardcoded to `net_gain` (Python waited for 3 buffers). Python
> blocked on its 2nd `Recv`, Fortran advanced into the next MPI loop → **hang**.
> Symptom in `log.run.*`: `[REWARD] INQURY  MODE= 0` (Fortran dudy) but Python
> logs `fn=net_gain`, then stops at `======== INTO MPI LOOP ============`.
> Fix: force `net_gain` (and `reward_{alpha,beta,gamma}`) on **both** the `initial`
> and `evaluate` launches in the eval branch (`execs/run-script`).

The weights come from the `reward_alpha/beta/gamma` shell variables at the top of
`run-script` (default `1.0`), applied identically to both launches.

> **Note:** the training / `run` branch does **not** force `reward_fn` — training
> uses the yaml value directly (single source of truth), which already writes a
> matching `.par`. Only the `evaluate` branch overrides, and only to `net_gain`.

## Verification checklist (mini_channel)

1. `./compile_script --all` (one-time recompile) — both reward paths compile.
2. **Train / `run` mode**, `reward_fn: dudy` → `.par` shows `userParam09 = 0`,
   log `REWARD MODE= 0`, single-buffer MPI path, training proceeds.
3. **Train / `run` mode**, `reward_fn: net_gain` → `.par` shows `userParam09 = 1`,
   log `REWARD MODE= 1`, 3-buffer MPI path, `reward_monitor00000.dat` written
   (GAINMONITOR).
4. **Evaluate mode** (any yaml `reward_fn`) → `.par` shows `userParam09 = 1`,
   log `REWARD MODE= 1` and Python `fn=net_gain` on *both* the `initial` and
   `evaluate` launches (run-script forces net_gain on both). Verified 2026-07-19:
   `reward_fn: dudy` yaml runs to completion (1000 steps) with no deadlock.
5. No MPI deadlock in any mode (Fortran `.par`/buffer count and Python receive
   path always agree by construction).

## Rollout status — all channel cases done

The runtime switch is now applied to **all channel-related cases** (2026-07-19).
Each still needs a **one-time recompile** (`./compile_script --all`) to pick up
the source changes; after that, dudy↔net_gain is a pure runtime choice.

**Converted (11 cases):**
`mini_channel` (first), `mini_channel_v`, `mini_channel_uv_invest`,
`lc_n7`, `lc_n11`, `lc_extra_n11`,
`lc_n7_jfm`, `lc_n11_jfm`, `lc_extra_n11_jfm`, `lc_n7_jfm_normp`, `lc_n7_jfm_pfluct`.

Two dispatch flavours were preserved verbatim inside the new `if (reward_mode.eq.1)`:
- **plain** cases call `compute_netGain(i_evolv)`.
- **`_jfm*`** cases call `compute_netGain_posOnly(i_evolv)` (position-only variant;
  the plain call stays commented out, exactly as before).

`drl/drl_IO.f` and `drl/drl_init.f` were byte-identical across all cases, so they
received the same edit. The batch edit script (exact-match, 1-substitution-per-edit
assertions) is at
`scratchpad/apply_runtime_switch.py` (session scratch) if a re-run is ever needed.

**Excluded on purpose:**
- `cluster_mini` — channel geometry but has **no** netgain machinery
  (`compute_netGain`, `/drl_netgain/` arrays absent); would need the full net_gain
  port first.
- `naca4412_*`, `small_wing*`, `naca0012_200k` — **wings, not channel**. They also
  have net_gain but do **not** use `UPARAM(8)` for `gll_unique`, so the free slot
  and init-echo anchor differ; convert separately if wanted.

**To convert a remaining case:**
1. Confirm `inc_src/DRL` declares `rwd_tau/rwd_pw/rwd_v3` (common `/drl_netgain/`).
2. Apply the same `!#[MOD]` edits to `drl/drl_reward.f`, `drl/drl_IO.f`,
   `drl/drl_init.f` — preserving that case's own net_gain call. **Pick a free
   UPARAM slot** (channel cases use 9 because 1–8 are taken; wings differ).
3. Remove `NETGAIN` from the case `compile_script` `PPLIST`; recompile once.

The Python side (`nek_utils.py`, `configs.py`) is shared and already done — every
case's `.par` now receives `userParam09` automatically (harmless for cases that
don't read it).
